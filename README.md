# ThermaSched

**An Integrated Optimization Model for Thermal-Aware Workload Scheduling and Air-Liquid
Cooling Control in Heterogeneous Data Centers.** DLSU Industrial Engineering thesis.

## Project summary

Data centers usually treat workload placement, server temperatures and cooling as
separate problems, but each one affects the others. Placing work on a server raises its
power and heat. Heat and cooling settings set the server's temperature. A hot server
throttles, which slows the work down and can make it miss its deadline. ThermaSched is a
mixed-integer linear program (MILP) that decides all of these together for one
heterogeneous, air- and liquid-cooled data center over a multi-period horizon (5-minute
periods). It decides:

- which server each workload runs on, and when it starts;
- whether waiting workloads are moved to another server;
- the CRAC supply-air temperature of each cooling zone in each period;
- the cold-plate coolant temperature and flow of each server that has cold plates.

The objective is to **minimize total operational carbon emissions** (IT, CRAC and
cold-plate energy times the grid's carbon intensity). Capacity, deadlines, allowable
delay, thermal headroom and cooling equipment limits are all hard constraints. Every run
is compared against a **baseline** schedule (a simple placement rule at a fixed supply
temperature), and both schedules are scored by the same evaluator.

The main scenario, **`thesis10`**, is the data center the thesis describes: ten
heterogeneous servers (four at 2.1 GHz, three at 2.4 GHz, three at 3.0 GHz) in two cooling
zones over 24 hours. Its results are the main results. The other scenarios are
experiments built from it, each changing one aspect (fleet size, deadlines, carbon
profile, cooling range), so each one reads as a difference from thesis10.

The inputs come from two datasets: **UniMelb** server telemetry supplies the
server parameters, and the **UFCG** OpenStack trace supplies the workloads. Deadlines,
zones, cold-plate placement and the daily carbon-intensity curve are generated by rule,
because no dataset provides them.

The project has three parts, each with its own guide:

| Part | What it does | Guide |
|---|---|---|
| **Cleaning notebook** | turns the raw datasets into cleaned tables and ready-to-solve scenarios | [`notebooks/README.md`](notebooks/README.md) |
| **Solver** | builds the baseline, solves the MILP with HiGHS, writes the comparison to `results/`; also runs step by step in `notebooks/solver.ipynb` | [`scheduler/README.md`](scheduler/README.md) |
| **Dashboard** | browser app to explore, compare and share the results | [`dashboard/README.md`](dashboard/README.md) |

```
raw data ──► notebooks/data_prep.ipynb ──► scenarios/ ──► scheduler (solver) ──► results/ ──► dashboard
```

The scenarios and a full set of results are already in the repository, so you can open
the dashboard or run the solver right away. The cleaning notebook is only needed to
change the data.

## Setup

Install [uv](https://docs.astral.sh/uv/getting-started/installation/), then from the
repository root:

```sh
uv sync          # creates .venv with Python >= 3.11 and every dependency
uv run pytest    # optional: checks that the install works
```

Then, for example:

```sh
uv run python -m scheduler.run --scenario small      # solve the small test scenario
uv run streamlit run dashboard/app.py                # open the dashboard at localhost:8501
```

Run every command from the repository root.

## Where to start

- **Look at the results:** start the dashboard, see [`dashboard/README.md`](dashboard/README.md).
  To publish it, see [Deploy on Streamlit Community Cloud](dashboard/README.md#5-deploy-on-streamlit-community-cloud).
- **Run a new scenario or setting:** see [`scheduler/README.md`](scheduler/README.md). To build
  a scenario with other settings or constants and solve it in one place, use
  [`notebooks/solver.ipynb`](notebooks/README.md#solver-notebook).
- **Change the data or how scenarios are built:** see [`notebooks/README.md`](notebooks/README.md).
- **Understand the model and its equations:** read
  [`docs/PROJECT_CONTEXT.md`](docs/PROJECT_CONTEXT.md); the known limitations of the
  current results are under [Current caveats](scheduler/README.md#8-current-caveats).
