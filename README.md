# ThermaSched

**An Integrated Optimization Model for Thermal-Aware Workload Scheduling and Air-Liquid
Cooling Control in Heterogeneous Data Centers.** DLSU Industrial Engineering thesis.

> **Plan going forward:** [`docs/PLAN.md`](docs/PLAN.md). Since 2026-10-25 the method is
> per-tick re-planning: the model re-solves every 5-minute period with only the workloads
> that have arrived. This README describes the code as it is today, which still solves the
> whole day at once; the whole-day results are in `archive/`.

## Project summary

Data centers usually treat workload placement, server temperatures and cooling as
separate problems, but each one affects the others. Placing work on a server raises its
power and heat. Heat and cooling settings set the server's temperature. A hot server
throttles, which slows the work down and can make it miss its deadline. ThermaSched is a
mixed-integer linear program (MILP) that decides all of these together for one
heterogeneous, air- and liquid-cooled data center over a multi-period horizon (5-minute
periods). It decides:

- which server each workload runs on, and when it starts;
- whether waiting workloads are moved to another server;
- the CRAC supply-air temperature of each cooling zone in each period;
- the cold-plate coolant temperature and flow of each server that has cold plates.

The objective is to **minimize total operational carbon emissions** (IT, CRAC and
cold-plate energy times the grid's carbon intensity). Capacity, deadlines, allowable
delay, thermal headroom and cooling equipment limits are all hard constraints. Every run
is compared against a **baseline** schedule (a simple placement rule at a fixed supply
temperature), and both schedules are scored by the same evaluator.

The scenarios are built from the data center the thesis describes, in two cooling zones over
24 hours. It has two server models in three speed tiers:

| Tier | Model | Frequency | Cooling | Cores | Memory |
|---|---|---|---|---|---|
| slow | Dell PowerEdge R840 | 2.1 GHz | CRAC | 64 | 64 GB |
| mid | Dell PowerEdge R840 | 2.4 GHz | CRAC | 64 | 64 GB |
| fast | Dell PowerEdge C6320 | 2.6 GHz | CRAC + cold plate | 80 | 193 GB |

The shipped scenarios are the six-server fleet (2 / 2 / 2 servers by tier) and the ten-server
fleet (3 / 4 / 3) on a light, normal and heavy day: **`servers6_light`**, **`servers6`**,
**`servers6_heavy`** and **`servers10_light`**, **`servers10`**, **`servers10_heavy`**, with
peak demand at 30, 60 and 85 % of the fleet's cores or memory, whichever fills first. Zones
alternate 1, 2, 1, ... in server order. The 2-server fleet is added when it is run.

The inputs come from two sources. **UniMelb** server telemetry (Zenodo 10069402) supplies
the server parameters (power, CPU temperature, cores and memory) from its two datasets of the
same cloud: D1 for the R840 servers and D2 for the C6320 servers. The **UFCG** OpenStack trace
supplies the workloads. Three values are assumptions, not data:

- **Frequencies** come from SPEC CPU results for these server models (2.1 GHz Xeon Gold 6130
  and 2.4 GHz Xeon Gold 6148 for the R840, 2.6 GHz Xeon E5-2690 v4 for the C6320); UniMelb
  does not name the processors.
- **Cores** are the hardware threads each model reported before the cloud doubled its vCPU
  slots in March 2019: 64 for the R840, 80 for the C6320.
- **C6320 inlet temperature** is borrowed from the R840 room: D2 has no inlet sensor, so each
  C6320 uses the mean measured R840 inlet at the same time.

Deadlines, zones, cold-plate placement and the daily carbon-intensity curve are generated by
rule, because no dataset provides them. The reasons for the fleet are in
[ADR 0001](docs/adr/0001-server-fleet-from-processor-specs.md).

The project has three parts, each with its own guide:

| Part | What it does | Guide |
|---|---|---|
| **Cleaning notebook** | turns the raw datasets into cleaned tables and ready-to-solve scenarios | [`notebooks/README.md`](notebooks/README.md) |
| **Solver** | builds the baseline, solves the MILP with HiGHS, writes the comparison to `results/`; runs step by step in `notebooks/solver.ipynb`, or a list of runs in `notebooks/batch.ipynb` | [`scheduler/README.md`](scheduler/README.md) |
| **Dashboard** | browser app with the Chapter 6 results (6.1 to 6.4) and every output CSV | [`dashboard/README.md`](dashboard/README.md) |

```
raw data ──► notebooks/data_prep.ipynb ──► scenarios/ ──► scheduler (solver) ──► results/ ──► dashboard
```

The scenarios are already in the repository, so you can run the solver right away.
`results/` is empty until the per-tick runs of [`docs/PLAN.md`](docs/PLAN.md) are solved; the
earlier whole-day results are in `archive/results_2026-10-25_whole_day/`. The cleaning notebook is only needed to
change the data. From the raw data it rebuilds the scenarios in the repository byte for
byte, and checks that it did (fingerprints, its section 4).

## Delivery to the thesis group

The thesis group gets the three notebooks and the link to the deployed dashboard (the
"site"), not the repository:

```
raw data (5 files, ~4 GB, shared by hand)
   │
   ▼
data_prep.ipynb ──► data/clean/, scenarios/        on their Google Drive (or laptop)
   │
   ▼
solver.ipynb (one run) or batch.ipynb (a list) ──► results/, exports/<run>.zip
   │
   ▼
to put a run on the site: they send the zip to the project owner, who unzips it into
results/ and pushes it to the release branch
```

Every scenario and run records the release that made it (`scheduler/version.py`), and every
run records a fingerprint of the scenario it was solved on, so the site can tell runs from
different releases or scenario builds apart.

## Releasing an update

The group works from a release, not from `main`. The site is deployed from the `release`
branch, so work in progress on `main` never reaches them.

1. Make the change on `main`. If it changes `scheduler/` or `dashboard/data.py`, `theme.py` or
   `uploads.py`, run `uv run python tools/sync_notebooks.py`. If it changes how scenarios are
   built, run `notebooks/data_prep.ipynb` too, then the sync again: it records the new
   scenario fingerprints in the notebook.
2. Raise the version in `pyproject.toml` and `scheduler/version.py` (`1.0.0` → `1.0.1` for a
   fix, `1.1.0` for a change in the results), and add a section to `CHANGELOG.md` that says
   what changed and what the group must re-run. If `summary.json` changed shape, raise
   `SCHEMA_VERSION` and keep the dashboard reading the older layout.
3. `uv run pytest` (it checks the notebooks, the version and the changelog), then commit.
4. Publish:

   ```sh
   git tag v1.0.1 && git push origin main v1.0.1
   git push origin main:release                     # the site redeploys from release
   gh release create v1.0.1 notebooks/data_prep.ipynb notebooks/solver.ipynb \
       notebooks/batch.ipynb --title "ThermaSched 1.0.1" --notes "<the CHANGELOG section>"
   ```

5. Tell the group: the release page has the new notebooks, and the changelog says what to
   re-run.

**Adding a run the group sent:** unzip it into `results/` (you get
`results/<scenario>/<run>/summary.json`, with the scenario's `servers.csv` and `carbon.csv`
next to the run folders), check it on the local dashboard, commit, and push `main` and
`release`. The site names a Chapter 6 run by its test whatever its folder; to match the
others, move it to `results/<configuration>/<test id>/` (for example
`results/servers10/s3_t1_hmin_high/`; the test ids are in `scheduler/experiments.py`). The
*Output files* page warns if it was solved on another scenario build than the one in
`scenarios/`.

## Setup

Install [uv](https://docs.astral.sh/uv/getting-started/installation/), then from the
repository root:

```sh
uv sync          # creates .venv with Python >= 3.11 and every dependency
uv run pytest    # optional: checks that the install works
```

Then, for example:

```sh
uv run python -m scheduler.run --scenario small      # solve the small test scenario
uv run streamlit run dashboard/app.py                # open the dashboard at localhost:8501
```

Run every command from the repository root.

## Where to start

- **Look at the results:** start the dashboard, see [`dashboard/README.md`](dashboard/README.md).
  To publish it, see [Deploy on Streamlit Community Cloud](dashboard/README.md#5-deploy-on-streamlit-community-cloud).
- **Run a new scenario or setting:** see [`scheduler/README.md`](scheduler/README.md). To build
  a scenario with other settings or constants and solve it in one place, use
  [`notebooks/solver.ipynb`](notebooks/README.md#solver-notebook).
- **Solve every thesis scenario in one go:** use
  [`notebooks/batch.ipynb`](notebooks/README.md#batch-notebook).
- **Ship an update to the thesis group:** see [Releasing an update](#releasing-an-update).
- **Change the data or how scenarios are built:** see [`notebooks/README.md`](notebooks/README.md).
- **Understand the model and its equations:** read
  [`docs/PROJECT_CONTEXT.md`](docs/PROJECT_CONTEXT.md); the known limitations of the
  current results are under [Current caveats](scheduler/README.md#8-current-caveats).
